Ce manuel explique comment configurer OD.MyLocalAgent, créer des tâches planifiées, utiliser les outils et comprendre les rapports — avec des procédures pas à pas pour les scénarios les plus courants.

Le parcours recommandé

Pour une première prise en main fiable, validez d’abord le fournisseur d’IA, créez ensuite une tâche locale sans compte externe, puis ajoutez les connecteurs uniquement lorsque vous en avez besoin.

Bien démarrer

Installation et prérequis

OD.MyLocalAgent s’exécute sur Windows 10 ou Windows 11 en 64 bits. La version publiée est autonome : elle n’exige pas l’installation séparée de .NET.

Prérequis essentiels

  • Windows 10 ou Windows 11, compte utilisateur habituel.
  • Ollama installé et son service démarré.
  • Au moins un modèle local, par défaut gemma4:12b.
  • Google et Dropbox uniquement si ces connecteurs sont utilisés.

Organisation publiée

L’interface et le runner sont volontairement séparés. Le runner est l’exécutable sans interface utilisé par Windows Task Scheduler. 

%LOCALAPPDATA%\Programs\OD.MyLocalAgent\
├── UI\OD.MyLocalAgent.UI.exe
└── Runner\OD.MyLocalAgent.Runner.exe

Préparer Ollama

Dans PowerShell, vérifiez Ollama et installez le modèle recommandé :

ollama --version
ollama pull gemma4:12b
ollama list
La ligne retournée par ollama list doit contenir exactement le tag choisi dans l’application. gemma4:12b et gemma4:latest sont deux identifiants différents.

Publier depuis le dépôt

Si vous disposez du code source, ouvrez PowerShell à la racine du dépôt et lancez : 

.\scripts\publish.ps1

Démarrez ensuite %LOCALAPPDATA%\Programs\OD.MyLocalAgent\UI\OD.MyLocalAgent.UI.exe.

Bien démarrer

Premier démarrage : la checklist

Effectuez ces contrôles dans l’ordre. Ils isolent les problèmes de modèle, de runner et de droits avant la création de tâches plus complexes.

  1. Ouvrez Settings.

    Conservez Ollama (local, default) pour le premier essai.

  2. Contrôlez l’endpoint et le modèle.

    L’endpoint local habituel est http://localhost:11434. Choisissez un modèle installé.

  3. Définissez File-system root path.

    Exemple : C:\OD.MyLocalAgent. Les outils fichiers seront confinés à ce dossier.

  4. Laissez Runner path vide.

    Dans l’installation standard, l’application trouve automatiquement le runner voisin.

  5. Enregistrez avec Save settings.

    Attendez le message confirmant la sauvegarde et le rechargement.

  6. Lancez Test connection.

    Le résultat doit indiquer que le fournisseur est sain et afficher une latence.

Les options Allow sending email, Allow file deletion et Allow HTTP POST sont désactivées par défaut. Ne les activez pas « au cas où » : attendez qu’un workflow précis en ait besoin.

Scénario guidé 01

Configurer Ollama et choisir un modèle

Ce scénario configure le fournisseur local par défaut et vérifie que le modèle sélectionné existe réellement dans Ollama.

  1. Ouvrez Settings → AI provider.

    Sélectionnez Ollama (local, default).

  2. Saisissez l’endpoint.

    Utilisez normalement http://localhost:11434. Pour un serveur Ollama distant autorisé, utilisez son URL HTTP ou HTTPS.

  3. Cliquez sur Refresh models.

    La liste est chargée depuis l’endpoint indiqué. Une indisponibilité est affichée sans basculer vers le cloud.

  4. Choisissez le modèle dans la combobox.

    La liste reste éditable, mais un tag saisi manuellement doit tout de même être installé côté Ollama.

  5. Conservez un délai adapté.

    La valeur par défaut de 300 secondes tient compte du premier token parfois lent d’un modèle local volumineux.

  6. Enregistrez puis testez.

    Cliquez sur Save settings, puis Test connection.

Un état sain signifie deux choses : l’endpoint répond et le modèle configuré figure dans la liste des modèles installés.

Scénario guidé 02

Créer une première tâche 100 % locale

Cette tâche crée un dossier, écrit un fichier puis le relit. Elle ne demande aucun compte cloud et valide le stockage, le workflow, le runner et les rapports.

  1. Préparez le dossier autorisé.

    Dans Settings, définissez File-system root path, par exemple C:\OD.MyLocalAgent, puis enregistrez.

  2. Ouvrez Tasks et cliquez sur New.

    L’éditeur de tâche s’ouvre.

  3. Renseignez l’identité.

    Id : first-local-task · Name : First local task. L’id accepte uniquement les lettres minuscules, chiffres et tirets.

  4. Ajoutez un prompt descriptif.

    Par exemple : « Verify the local filesystem workflow and report the result. »

  5. Choisissez une planification.

    Dans Quick schedule, sélectionnez Every day at 09:00. Vérifiez les trois prochaines occurrences.

  6. Autorisez uniquement File system.

    Dans Tool whitelist, laissez les autres outils décochés.

  7. Collez le workflow ci-dessous dans Workflow JSON.

    Le champ attend un tableau JSON de étapes, et non l’objet complet de la tâche.

[
  {
    "step": "filesystem.createDirectory",
    "id": "createWelcomeDirectory",
    "args": {
      "path": "welcome"
    }
  },
  {
    "step": "filesystem.write",
    "id": "writeWelcomeFile",
    "args": {
      "path": "welcome/hello.txt",
      "content": "OD.MyLocalAgent completed {{task.id}}."
    }
  },
  {
    "step": "filesystem.read",
    "id": "readWelcomeFile",
    "args": {
      "path": "welcome/hello.txt"
    }
  }
]
  1. Laissez la tâche activée et enregistrez.

    Cliquez sur Save task. La syntaxe, les alias, les arguments et la liste blanche sont validés.

  2. Exécutez-la immédiatement.

    Revenez à Tasks, sélectionnez la ligne et cliquez sur Run now.

  3. Contrôlez le résultat.

    Le panneau Runner output doit confirmer le succès. Le fichier welcome\hello.txt apparaît sous la racine configurée.

Pourquoi cette tâche est sûre : elle ne dispose que du groupe filesystem, les chemins restent relatifs à la racine autorisée et aucune suppression n’est demandée.

Scénario guidé 03

Tester un prompt, puis lancer la vraie tâche

Le test de prompt permet d’itérer rapidement avec une réponse en streaming. Run now utilise ensuite le même runner que la planification Windows.

  1. Dans Tasks, sélectionnez une tâche.

    Cliquez sur Prompt.

  2. Modifiez le texte dans Agent prompt.

    Précisez le résultat attendu, le format et les limites. Exemple : longueur maximale, langue, rubriques obligatoires.

  3. Cliquez sur Save prompt.

    Le texte est enregistré dans la définition de la tâche.

  4. Lancez Test the prompt.

    La réponse apparaît progressivement dans Streamed agent output. Le test utilise la liste blanche d’outils de la tâche.

  5. Ajustez et recommencez si nécessaire.

    Utilisez Cancel pour interrompre une génération trop longue.

  6. Revenez à Tasks et cliquez sur Run now.

    Si un workflow existe, il est prioritaire. Sans workflow, le runner exécute le prompt avec les outils autorisés.

Test de prompt ≠ test du workflow. Le bouton Test the prompt teste l’agent et la liste blanche. Run now exécute le chemin réel de la tâche et crée le rapport normal.

Scénario guidé 04

Connecter Gmail et Google Calendar

L’autorisation Google est interactive et doit être réalisée dans l’interface sous le même compte Windows que celui qui exécutera les tâches planifiées.

Préparer Google Cloud

  1. Créez ou sélectionnez un projet Google Cloud.

    Activez Gmail API et Google Calendar API.

  2. Configurez l’écran de consentement OAuth.

    Ajoutez votre compte comme utilisateur de test tant que l’application reste en mode test.

  3. Créez un client OAuth de type Desktop app.

    Copiez le Client ID et le Client Secret.

  4. Fermez OD.MyLocalAgent et complétez settings.json.

    Conservez les autres sections du fichier et ajoutez ou mettez à jour la section suivante.

{
  "Google": {
    "ClientId": "YOUR_DESKTOP_CLIENT_ID",
    "ClientSecret": "YOUR_DESKTOP_CLIENT_SECRET"
  }
}

Le fichier se trouve dans %LOCALAPPDATA%\OD.MyLocalAgent\settings.json.

Autoriser dans l’application

  1. Relancez l’application et ouvrez Tools.

    La section Google Workspace doit indiquer que la configuration OAuth est disponible.

  2. Cliquez sur Connect.

    Terminez le consentement dans le navigateur avec le compte Google voulu.

  3. Revenez dans l’application et actualisez le statut.

    Utilisez Refresh status si nécessaire.

  4. Testez Gmail et Calendar séparément.

    Chaque bouton Test connection effectue une opération en lecture seule et affiche la latence.

  5. Dans la tâche, cochez seulement Gmail et/ou Calendar.

    L’autorisation OAuth ne remplace pas la liste blanche de chaque tâche.

Lire les messages et envoyer un message sont deux capacités différentes. gmail.send reste bloqué tant que Allow sending email n’est pas explicitement activé dans Settings.

Scénario guidé 05

Connecter Dropbox

Les valeurs Dropbox sont saisies en écriture seule puis protégées par DPAPI pour le compte Windows courant.

  1. Créez une application dans Dropbox App Console.

    Choisissez l’accès le plus limité possible, idéalement un dossier d’application.

  2. Activez uniquement les permissions nécessaires.

    Lecture de métadonnées, lecture de contenu et écriture selon les alias utilisés.

  3. Obtenez les identifiants.

    Utilisez soit un access token, soit un refresh token accompagné de l’app key.

  4. Ouvrez Tools → Dropbox.

    Saisissez les nouvelles valeurs dans les champs prévus.

  5. Cliquez sur Save credentials.

    Les secrets sont chiffrés pour l’utilisateur Windows courant et ne sont pas écrits dans settings.json.

  6. Lancez Test connection.

    Le test effectue une opération de lecture seule.

  7. Ajoutez Dropbox à la tâche concernée.

    Cochez Dropbox dans Tool whitelist et utilisez un alias dropbox.* dans le workflow.

Scénario guidé 06 · Activation cloud

Activer la recherche web Ollama protégée

Web Search est désactivé sur une installation neuve. Les requêtes et les extraits reçus quittent l’ordinateur vers l’endpoint cloud Ollama configuré.

  1. Créez un compte ollama.com et obtenez une clé Web Search.

    L’offre individuelle gratuite peut être limitée, surtout lors de rafales de requêtes.

  2. Ouvrez Tools → Web search (cloud).

    Activez la recherche et conservez normalement https://ollama.com/api/web_search.

  3. Collez la clé en écriture seule puis sélectionnez Save.

    DPAPI protège la clé, qui n’est jamais écrite dans settings.json. Un endpoint personnalisé reçoit la clé et les requêtes.

  4. Sélectionnez Test connection.

    Le test à requête fixe affiche seulement la durée et le nombre de résultats, jamais les extraits.

  5. Activez Web search (web) (cloud) dans la tâche.

    Utilisez web.search avec query obligatoire et maxResults facultatif (5 par défaut, 10 maximum).

Les résultats sont des données externes non fiables. Titres et extraits sont bornés, contrôlés exactement une fois et renvoyés dans une seule enveloppe protectedResults. Le dépassement est explicitement tronqué ou omis. Index et URL sont des métadonnées supprimées si Guardrails masque le contenu. Un contrôle désactivé ou en échec reste en Base64 marqué, jamais en texte brut.

Scénario guidé 07

Explorer un prompt dans l’AI playground

Le playground sert aux essais libres. Son mode par défaut appelle directement le fournisseur ; les outils et les skills demandent chacun une autorisation explicite.

  1. Ouvrez AI playground.

    Le badge en haut indique le fournisseur et le modèle actifs.

  2. Cliquez sur Check health.

    Résolvez d’abord un endpoint ou un modèle indisponible.

  3. Saisissez un prompt.

    Sans case cochée, la réponse est une complétion brute, sans outil ni skill.

  4. Choisissez les capacités nécessaires.

    Cochez Allow Tools et/ou Allow Skills seulement si le test l’exige.

  5. Cliquez sur Generate.

    La réponse apparaît progressivement. Cancel interrompt la génération.

Allow Tools Allow Skills Mode obtenu
NonNonComplétion brute du fournisseur.
OuiNonAgent avec les six groupes d’outils.
NonOuiAgent avec summarize, extract action items et classify email.
OuiOuiAgent avec outils et skills intégrés.
Allow Tools donne accès à tous les groupes dans ce test interactif, mais les garde-fous globaux restent actifs : sandbox fichiers, hôtes HTTP autorisés et options Safety.

Scénario guidé 07

Tester un outil isolément

Tool tester exécute un alias précis avec des arguments JSON explicites. C’est le moyen le plus direct de vérifier une connexion ou un garde-fou.

  1. Ouvrez Tool tester.

    Sélectionnez un alias dans la liste.

  2. Lisez l’indication des arguments.

    Le formulaire rappelle les noms attendus par l’alias.

  3. Saisissez un objet JSON.

    Pour lister la racine de la sandbox, choisissez filesystem.list et utilisez l’exemple ci-dessous.

{
  "path": "."
}
  1. Cliquez sur Run tool.

    Le résultat formaté et la durée s’affichent à droite.

  2. En cas de blocage, lisez le nom du réglage.

    Une opération protégée indique précisément l’option Safety requise. N’activez cette option qu’après vérification.

Commencez par des alias sans effet de bord : filesystem.list, filesystem.read, gmail.readUnread, calendar.today ou dropbox.list.

Scénario guidé 08

Activer un fournisseur OpenAI-compatible

Le cloud est un choix explicite. Dès qu’il est sélectionné, les prompts et le contexte utile sont envoyés à l’endpoint configuré.

  1. Ouvrez Settings → AI provider.

    Sélectionnez OpenAI-compatible (cloud, opt-in).

  2. Vérifiez l’avertissement cloud.

    Assurez-vous que la politique de confidentialité de l’endpoint convient aux données traitées.

  3. Renseignez Endpoint, Model et Timeout.

    Pour OpenAI, l’endpoint par défaut est https://api.openai.com/v1. Un serveur compatible peut utiliser une autre URL.

  4. Saisissez la clé dans Replace API key.

    Le champ reste vide après sauvegarde : la clé est écrite dans le magasin DPAPI, jamais réaffichée.

  5. Cliquez sur Save settings.

    Le fournisseur s’applique aux prochains tests et exécutions, sans redémarrage.

  6. Lancez Test connection.

    Une erreur de clé, d’endpoint ou de modèle est affichée comme telle ; aucun retour silencieux vers Ollama n’a lieu.

La clé API ne doit jamais être ajoutée manuellement à appsettings.json ou settings.json. Utilisez exclusivement le champ protégé de l’application.

Référence

Tâches, prompts et workflows

Une tâche associe une identité, une planification, un prompt, une liste blanche d’outils et éventuellement un workflow déterministe.

Prompt seul

L’agent interprète l’objectif et peut choisir parmi les outils autorisés. Ce mode est souple, mais le comportement de tool-calling dépend du modèle.

Workflow

Les étapes sont exécutées dans l’ordre défini. C’est le mode recommandé pour les automatisations sans surveillance. Si prompt et workflow coexistent, le workflow est prioritaire.

Forme d’une tâche

{
  "id": "daily-mail-summary",
  "name": "Daily mail summary",
  "schedule": "0 7 * * *",
  "prompt": "Summarize today's important messages.",
  "tools": ["gmail", "filesystem"],
  "fileSystemAccess": [],
  "workflow": [
    "gmail.readToday",
    {
      "step": "ai.summarize",
      "id": "summary"
    },
    {
      "step": "filesystem.write",
      "args": {
        "path": "reports/mail-summary.md",
        "content": "{{summary.output.text}}"
      }
    }
  ],
  "enabled": true,
  "errorPolicy": "StopOnError"
}

Règles importantes

  • L’id suit le format [a-z0-9-]+ et devient immuable après création.
  • Le prompt peut être vide uniquement si le workflow contient au moins une étape.
  • Un alias d’outil exige que son groupe soit coché dans Tool whitelist.
  • Un skill ai.* est toujours autorisé dans un workflow.
  • Les chemins relatifs restent sous le RootPath configuré.
  • Un chemin absolu exige un emplacement autorisé appartenant à la tâche.

Emplacements autorisés

L’éditeur permet d’autoriser pour cette tâche des dossiers absolus supplémentaires, sans créer de catalogue global. Chaque règle inclut ses sous-dossiers et accorde ReadOnly ou ReadWrite. Une liste vide n’autorise aucun chemin absolu. Les droits Windows restent prioritaires. 

"fileSystemAccess": [
  {
    "path": "D:\\Production\\Incoming",
    "access": "ReadOnly"
  },
  {
    "path": "E:\\Archives\\Daily",
    "access": "ReadWrite"
  }
]

Étapes, sorties et placeholders

Une étape sous forme de chaîne ne prend aucun argument. La forme objet accepte step, id, args et une politique d’erreur. Les placeholders sont remplacés juste avant l’exécution de l’étape.

PlaceholderValeur
{{task.id}}Id de la tâche.
{{task.name}}Nom de la tâche.
{{task.prompt}}Prompt enregistré.
{{previous.output}}Sortie de l’étape précédente.
{{stepId.output}}Sortie d’une étape désignée par son id.
{{stepId.output.property}}Propriété extraite d’une sortie JSON ; les index de tableau comme items[0].name sont acceptés.
{{workflow.context}}Instantané JSON de toutes les sorties réussies accumulées jusque-là.
{{Today}}Date locale courante au format yyyy-MM-dd.
{{Today[format]}}Date locale avec le format demandé, par exemple {{Today[YYYY]}} ou {{Today[yyyyMMdd]}}.
{{Now}}Date et heure locales au format yyyy-MM-ddTHH:mm:sszzz.
{{Now[format]}}Date et heure locales avec le format demandé, par exemple {{Now[hhmmss]}}.

Les délimiteurs sont exactement deux accolades ouvrantes et deux accolades fermantes : {{placeholder}}. Un placeholder peut être seul ou entouré de texte dans toute valeur chaîne située sous args. La résolution parcourt les objets et tableaux, mais ne modifie ni les noms de propriétés JSON, ni les nombres, ni les booléens. Les noms et propriétés JSON sélectionnées ne sont pas sensibles à la casse. Il n’existe pas d’échappement pour écrire littéralement {{...}} : toute séquence de ce type est interprétée et un nom inconnu fait échouer l’étape.

Les sélecteurs structurés commencent après .output. Un point sélectionne une propriété d’objet et [0] un élément de tableau avec un index commençant à zéro. Par exemple, {{files.output.entries[0].name}} retourne le nom du premier fichier. Une propriété absente, un index invalide ou une sélection structurée appliquée à du texte simple fait échouer l’étape.

Les dates utilisent le fuseau Windows local. Les crochets contiennent un format personnalisé .NET. Pour les noms de fichiers, les alias YYYY, YY, DD et hh signifient yyyy, yy, dd et HH sur 24 heures. Évitez / et : dans un nom de fichier Windows. 

{
  "path": "reports/{{Today[YYYY]}}/triage-{{Now[yyyyMMdd-hhmmss]}}.md",
  "content": "{{triage.output.text}}"
}

Politiques d’erreur

PolitiqueComportement
StopOnErrorArrête le workflow dès la première erreur.
ContinueOnErrorEnregistre l’échec et poursuit les étapes suivantes.
RetryRéessaie selon retryCount et un délai exponentiel basé sur retryBackoffSeconds.

Renommer un fichier et changer son extension

filesystem.rename accepte uniquement un nom simple et conserve le dossier courant. filesystem.setExtension garde le nom de base et accepte une extension avec ou sans point initial. Les deux opérations exigent un accès en lecture-écriture, refusent une destination existante et retournent un chemin JSON to réutilisable par l’étape suivante. 

[
  {
    "step": "filesystem.rename",
    "id": "rename",
    "args": {
      "path": "incoming/report.tmp",
      "newName": "report-{{Today[yyyyMMdd]}}.tmp"
    }
  },
  {
    "step": "filesystem.setExtension",
    "args": {
      "path": "{{rename.output.to}}",
      "extension": ".md"
    }
  }
]

Utiliser l’extraction et la classification sans boucle

Ces deux skills appellent le LLM sans outil. Si args.text est omis, ils reçoivent la sortie complète de l’étape précédente ; placés en première étape, ils reçoivent le prompt de la tâche. Une valeur text explicite est prioritaire. Ils peuvent donc traiter en un seul appel tout le lot retourné par gmail.readUnread, sans boucle de workflow. Leur sortie suit la forme {"text":"..."} ; utilisez {{stepId.output.text}} pour insérer uniquement le Markdown.

ai.classifyEmail crée une ligne par message identifiable avec Message, Category, Reason et Deadline. Il produit seulement un rapport global : il ne crée pas de branche et ne peut pas lancer une opération différente pour chaque catégorie. 

[
  "gmail.readUnread",
  { "step": "ai.classifyEmail", "id": "triage" },
  {
    "step": "filesystem.write",
    "args": {
      "path": "reports/mail-triage-{{Today[yyyyMMdd]}}.md",
      "content": "{{triage.output.text}}"
    }
  }
]

ai.extractActionItems suit le même schéma par lot. Il retourne des cases Markdown contenant seulement les actions explicites et écrit Not stated lorsqu’un responsable, une échéance ou une source manque. Sans action explicite, il retourne exactement No explicit action items. 

[
  "gmail.readUnread",
  { "step": "ai.extractActionItems", "id": "actions" },
  {
    "step": "filesystem.write",
    "args": {
      "path": "reports/actions-{{Now[yyyyMMdd-HHmmss]}}.md",
      "content": "{{actions.output.text}}"
    }
  }
]

Planification et format cron

L’éditeur propose des horaires courants en langage clair. Pour un besoin avancé, le champ cron reste éditable et l’aperçu calcule les trois prochaines occurrences dans le fuseau local Windows.

Les cinq champs

minute   heure   jour-du-mois   mois   jour-de-semaine
 0-59     0-23       1-31       1-12        0-6

* signifie « toutes les valeurs », */n un intervalle, la virgule une liste et le tiret une plage. Le dimanche vaut 0.

ExpressionSignification
*/5 * * * *Toutes les 5 minutes.
0 * * * *Au début de chaque heure.
0 7 * * *Tous les jours à 07:00.
0 9 * * 1-5Du lundi au vendredi à 09:00.
0 9 * * 1Chaque lundi à 09:00.
0 9 1 * *Le premier jour de chaque mois à 09:00.

Enabled et Registered

Enabled

État enregistré dans la définition de la tâche. Une tâche Enabled doit être planifiée et sera réparée par une resynchronisation.

Registered

Indique si le miroir existe actuellement dans Windows Task Scheduler. Le bouton Register/Unregister agit sur ce miroir.

La définition JSON reste la source de vérité. Windows Task Scheduler ne contient que la prochaine occurrence. Après chaque exécution, le runner calcule et enregistre la suivante. Utilisez Resync schedules pour réparer des enregistrements supprimés ou obsolètes.

Exécution lorsque l’utilisateur est déconnecté

Dans Settings, l’option Run when the user is logged off (S4U) permet une exécution sans session interactive. Elle doit rester associée au même compte Windows, car les secrets DPAPI, les tokens Google et %LOCALAPPDATA% dépendent de cet utilisateur.

S4U ne peut pas afficher le consentement Google. Connectez Google depuis l’interface avant d’activer ce mode.

Protection contre la prompt injection

Comprendre le filtre de confiance

Les lectures Gmail et les réponses http.get / http.getText sont classées par un appel LLM direct, sans outil, skill ni boucle d’agent. Cette réduction du risque est probabiliste : elle ne remplace jamais les limites Safety, la liste blanche d’outils, le bac à sable fichiers ou la liste d’hôtes HTTP.

Score/statutLivraison au modèle
Clean, 80–100 par défautTexte marqué entre délimiteurs UNTRUSTED-EXTERNAL-DATA.
Caution, 50–79UTF-8 Base64 marqué entre délimiteurs UNTRUSTED-EXTERNAL-DATA-BASE64.
Low, 0–49Contenu retenu et remplacé par un marqueur avec le score.
ScreeningDisabled / FailedBase64 marqué pour un contenu de taille normale.
Base64 n’est ni du chiffrement ni une frontière de sécurité. Le modèle peut le décoder et doit toujours traiter le texte décodé comme une donnée, jamais comme une instruction.

Contenus volumineux

Au-delà de MaxContentChars, chaque caractère de la source est couvert par des morceaux ordonnés et des appels séquentiels sans outil. Le score final est le minimum observé sur la source et sur le bloc résumé livré. Un résumé trop long est tronqué en C# avec un marqueur explicite et passe obligatoirement en Base64. Au-delà de MaxSummarizationSourceChars, aucune synthèse partielle n’est produite.

  • Gmail conserve exactement From, To, Subject et Snippet dans un bloc canonique protégé, puis remplace seulement Body par un résumé ou un avis de relecture Gmail.
  • HTTP conserve URL, code de statut et type de contenu, puis renvoie un avis Skipped… sans page ni résumé partiel.
  • Une limite Gmail positive traite seulement les N premiers messages avec des compteurs et un avertissement ; 0 signifie illimité.

Page Trust filter

Collez un exemple externe, choisissez éventuellement Return Base64, puis cliquez sur Screen. La page distingue le statut de confiance du statut de traitement, montre score, fournisseur, latence, longueurs, aperçu protégé et indicateurs verbatim. Ces indicateurs restent réservés à cette page ; les sorties Gmail/HTTP/Web Search n’exposent que leur nombre.

Réglages, confidentialité et limites

La section Settings → General → Guardrails règle les seuils, tailles, synthèse, délai, cache de 24 heures et limite Gmail. Désactiver Use LLM guardrails processing ne désactive pas la protection : le chemin normal utilise Base64 et les sources volumineuses appliquent les avis Gmail/HTTP.

Avec OpenAI-compatible, le contenu Gmail/HTTP/Web Search classé quitte la machine. Une source volumineuse peut être envoyée intégralement par plusieurs morceaux successifs. N’utilisez pas de véritable courrier privé pendant un test cloud sans autorisation explicite.

Les faux positifs et faux négatifs restent possibles, notamment face aux charges codées ou obfusquées. Dropbox, fichiers locaux, Calendar, pièces jointes Gmail, contenus sortants et réponses HTTP POST sont hors périmètre.

Sécurité : autoriser le minimum nécessaire

La sécurité repose sur plusieurs couches complémentaires. Une connexion valide ne suffit jamais à autoriser automatiquement une tâche.

CoucheRôle

Safety gates Bloque par défaut l’envoi d’e-mail, la suppression de fichier et HTTP POST.
File-system root path Confine les opérations utilisant un chemin relatif sous une racine absolue.

HTTP Allowed Hosts Limite les destinations HTTP par nom d’hôte exact.
DPAPI CurrentUser Protège les clés OpenAI, Dropbox et Web Search pour le compte Windows courant.

Les e-mails, pages web et fichiers lus par les outils sont des données non fiables. Ils peuvent contenir des instructions malveillantes destinées au modèle. Ne donnez pas à une tâche plus de droits que son workflow n’en exige.

Liste d’hôtes HTTP

Dans Allowed HTTP hosts, saisissez les noms d’hôtes séparés par des virgules, sans protocole ni chemin. Une liste vide autorise tous les hôtes HTTP/HTTPS : c’est pratique pour un test, mais déconseillé pour une tâche sans surveillance.

Diagnostics, exports et incidents

La section Diagnostics se trouve en bas de Settings. Elle permet d’exporter les éléments utiles à une analyse sans arrêter l’application.

Journaux de l’application

Save to disk…

Exporte l’intégralité du tampon de logs actuellement visible vers un fichier .log choisi par l’utilisateur.

Reset

Après confirmation, efface la vue, copie les journaux courants dans une archive horodatée et tronque les fichiers actifs.

Incidents

Un incident contient l’heure UTC, la gravité, la source, le message, la pile d’appels et un correlation id. Ce dernier permet de relier la notification visible à l’enregistrement durable.

  • Copy details copie toutes les informations d’un incident.
  • Export… sauvegarde la liste.
  • Clear all efface les incidents après confirmation.
  • Trigger test incident vérifie volontairement le pipeline d’erreur.
Utilisez Trigger test incident uniquement pour un diagnostic volontaire. L’incident créé est réel et restera dans la liste tant qu’il n’est pas effacé.

Assistance

Résoudre les problèmes courants

Ouvrez un sujet pour afficher les contrôles recommandés, dans l’ordre.

Ollama ne répond pas
  1. Lancez ollama list dans PowerShell.
  2. Vérifiez que l’endpoint est http://localhost:11434 pour une installation locale standard.
  3. Dans Settings, cliquez sur Refresh models.
  4. Enregistrez, puis lancez Test connection.
  5. Consultez Logs si le service répond en ligne de commande mais pas dans l’application.
Le modèle configuré est absent

Installez le tag manquant, puis actualisez la liste :

ollama pull gemma4:12b
ollama list

Choisissez exactement le même identifiant dans la combobox Ollama.

Le runner est introuvable
  1. Vérifiez que le dossier publié contient Runner\OD.MyLocalAgent.Runner.exe.
  2. Laissez Runner path vide pour la disposition standard UI/Runner.
  3. Sinon, saisissez le chemin absolu du runner publié.
  4. Enregistrez Settings et lancez Resync schedules.
Une tâche n’est plus planifiée ou indique Registered = No
  1. Vérifiez que la tâche est Enabled.
  2. Sélectionnez-la dans Tasks et utilisez Register si vous ne voulez réparer que cette tâche.
  3. Pour une réparation globale, utilisez Dashboard → Resync schedules.
  4. Actualisez Tasks et vérifiez la prochaine occurrence.
Google demande sans cesse le consentement
  1. Vérifiez que le client OAuth est de type Desktop app.
  2. Confirmez que le compte est autorisé comme utilisateur de test.
  3. Vérifiez que Gmail API et Calendar API sont activées.
  4. Effectuez le consentement depuis Tools dans une session Windows interactive.
  5. Utilisez le même compte Windows pour les tâches S4U.
Une opération est bloquée par SafetyException

Lisez le nom exact du réglage demandé. Vérifiez le workflow, la liste blanche, la destination et les données d’entrée. Activez ensuite uniquement l’option nécessaire dans Settings → Safety gates.

Un chemin fichier est refusé

Utilisez un chemin relatif comme reports\summary.md pour RootPath, ou ajoutez le dossier absolu dans Authorized locations de la tâche. Vérifiez le mode lecture/écriture, les droits Windows et la disponibilité du volume. Les remontées ..\ restent refusées.

Une requête HTTP est refusée
  1. Vérifiez le nom d’hôte dans Allowed HTTP hosts, sans protocole ni chemin.
  2. Pour POST, activez Allow HTTP POST après vérification du contenu.
  3. Pour GET, contrôlez l’URL et le certificat de l’endpoint.
  4. Utilisez Tool tester pour isoler l’appel.
