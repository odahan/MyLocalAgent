Votre agent local,

Le parcours recommandé

Pour une première prise en main fiable, validez d’abord le fournisseur d’IA, créez ensuite une tâche locale sans compte externe, puis ajoutez les connecteurs uniquement lorsque vous en avez besoin.

Automatiser

Bien démarrer

Installation et prérequis

OD.MyLocalAgent s’exécute sur Windows 10 ou Windows 11 en 64 bits. La version publiée est autonome : elle n’exige pas l’installation séparée de .NET.

Prérequis essentiels

  • Windows 10 ou Windows 11, compte utilisateur habituel.
  • Ollama installé et son service démarré.
  • Au moins un modèle local, par défaut gemma4:12b.
  • Google et Dropbox uniquement si ces connecteurs sont utilisés.

Organisation publiée

L’interface et le runner sont volontairement séparés. Le runner est l’exécutable sans interface utilisé par Windows Task Scheduler. 

%LOCALAPPDATA%\Programs\OD.MyLocalAgent\
├── UI\OD.MyLocalAgent.UI.exe
└── Runner\OD.MyLocalAgent.Runner.exe

Préparer Ollama

Dans PowerShell, vérifiez Ollama et installez le modèle recommandé :

ollama --version
ollama pull gemma4:12b
ollama list
La ligne retournée par ollama list doit contenir exactement le tag choisi dans l’application. gemma4:12b et gemma4:latest sont deux identifiants différents.

Publier depuis le dépôt

Si vous disposez du code source, ouvrez PowerShell à la racine du dépôt et lancez : 

.\scripts\publish.ps1

Démarrez ensuite %LOCALAPPDATA%\Programs\OD.MyLocalAgent\UI\OD.MyLocalAgent.UI.exe.

Bien démarrer

Premier démarrage : la checklist

Effectuez ces contrôles dans l’ordre. Ils isolent les problèmes de modèle, de runner et de droits avant la création de tâches plus complexes.

  1. Ouvrez Settings.

    Conservez Ollama (local, default) pour le premier essai.

  2. Contrôlez l’endpoint et le modèle.

    L’endpoint local habituel est http://localhost:11434. Choisissez un modèle installé.

  3. Définissez File-system root path.

    Exemple : C:\OD.MyLocalAgent. Les outils fichiers seront confinés à ce dossier.

  4. Laissez Runner path vide.

    Dans l’installation standard, l’application trouve automatiquement le runner voisin.

  5. Repérez les utilitaires de dossiers et de raccourci.

    Les icônes de copie placent séparément les dossiers des rapports et de l’exécutable dans le presse-papiers. Create desktop shortcut crée ou actualise le raccourci de l’interface sur le Bureau Windows.

  6. Enregistrez avec Save settings.

    Attendez le message confirmant la sauvegarde et le rechargement.

  7. Lancez Test connection.

    Le résultat doit indiquer que le fournisseur est sain et afficher une latence.

Les options Allow sending email, Allow file deletion et Allow HTTP POST sont désactivées par défaut. Ne les activez pas « au cas où » : attendez qu’un workflow précis en ait besoin.

Scénario guidé 01

Configurer Ollama et choisir un modèle

Ce scénario configure le fournisseur local par défaut et vérifie que le modèle sélectionné existe réellement dans Ollama.

  1. Ouvrez Settings → AI provider.

    Sélectionnez Ollama (local, default).

  2. Saisissez l’endpoint.

    Utilisez normalement http://localhost:11434. Pour un serveur Ollama distant autorisé, utilisez son URL HTTP ou HTTPS.

  3. Cliquez sur Refresh models.

    La liste est chargée depuis l’endpoint indiqué. Une indisponibilité est affichée sans basculer vers le cloud.

  4. Choisissez le modèle dans la combobox.

    La liste reste éditable, mais un tag saisi manuellement doit tout de même être installé côté Ollama.

  5. Vérifiez AI generation defaults.

    Les valeurs initiales sont Temperature 0.2, Top P 1 et Context window 8192. Les plages sont respectivement 0–2, plus de 0 jusqu’à 1, et 1024–2000000. Modifiez d’abord Temperature ou Top P, plutôt que les deux.

  6. Définissez, si nécessaire, des instructions IA globales.

    Dans Project-wide AI instructions, écrivez uniquement les conventions durables du projet, telles que la langue de réponse ou le format de sortie. Dans l’éditeur de tâche, la case Apply project-wide AI instructions to this task est activée par défaut ; décochez-la pour exclure une tâche. Le bouton View system prompt affiche le texte configuré ou l’état d’exclusion. Les règles de sécurité intégrées, les outils autorisés et la tâche restent prioritaires.

  7. Conservez un délai adapté.

    La valeur par défaut de 300 secondes tient compte du premier token parfois lent d’un modèle local volumineux.

  8. Enregistrez puis testez.

    Cliquez sur Save settings, puis Test connection.

Un état sain signifie deux choses : l’endpoint répond et le modèle configuré figure dans la liste des modèles installés.
Context window représente le budget total déclaré — messages, contexte agent/outils et réponse — et non une limite de tokens de sortie. Ollama reçoit cette valeur via son option native num_ctx. Un fournisseur OpenAI-compatible reste maître de sa capacité fixe ; aucun champ non pris en charge ne lui est envoyé.

Scénario guidé 02

Créer une première tâche 100 % locale

Cette tâche crée un dossier, écrit un fichier puis le relit. Elle ne demande aucun compte cloud et valide le stockage, le workflow, le runner et les rapports.

  1. Préparez le dossier autorisé.

    Dans Settings, définissez File-system root path, par exemple C:\OD.MyLocalAgent, puis enregistrez.

  2. Ouvrez Tasks et cliquez sur New.

    L’éditeur de tâche s’ouvre.

  3. Renseignez l’identité.

    Id : first-local-task · Name : First local task. L’id accepte uniquement les lettres minuscules, chiffres et tirets.

  4. Ajoutez un prompt descriptif.

    Par exemple : « Verify the local filesystem workflow and report the result. »

  5. Choisissez une planification.

    Dans Quick schedule, sélectionnez Every day at 09:00. Vérifiez les trois prochaines occurrences.

  6. Autorisez uniquement File system.

    Dans Tool whitelist, laissez les autres outils décochés.

  7. Collez le workflow ci-dessous dans Workflow JSON.

    Le champ attend un tableau JSON de étapes, et non l’objet complet de la tâche.

La liste Tool whitelist est générée depuis le catalogue d’outils compilé dans cette version. Les nouveaux groupes intégrés à une future version apparaissent donc automatiquement dans cet éditeur, toujours décochés par défaut. Cocher un groupe ne crée aucune autorisation de chemin et ne modifie aucun réglage Safety ; ces contrôles restent indépendants. Ce catalogue ne charge pas de plug-ins externes à l’exécution. 
[
  {
    "step": "filesystem.createDirectory",
    "id": "createWelcomeDirectory",
    "args": {
      "path": "welcome"
    }
  },
  {
    "step": "filesystem.write",
    "id": "writeWelcomeFile",
    "args": {
      "path": "welcome/hello.txt",
      "content": "OD.MyLocalAgent completed {{task.id}}."
    }
  },
  {
    "step": "filesystem.read",
    "id": "readWelcomeFile",
    "args": {
      "path": "welcome/hello.txt"
    }
  }
]
  1. Laissez la tâche activée et enregistrez.

    Cliquez sur Save task. La syntaxe, les alias, les arguments et la liste blanche sont validés. Si la définition est incomplète ou invalide, une boîte de dialogue l’explique et aucune modification n’est enregistrée. Back demande confirmation avant d’abandonner un brouillon modifié.

  2. Exécutez-la immédiatement.

    Revenez à Tasks, sélectionnez la ligne et cliquez sur Run now.

  3. Contrôlez le résultat.

    Le panneau Runner output doit confirmer le succès. Le fichier welcome\hello.txt apparaît sous la racine configurée.

Pourquoi cette tâche est sûre : elle ne dispose que du groupe filesystem, les chemins restent relatifs à la racine autorisée et aucune suppression n’est demandée.

Scénario guidé 03

Tester un prompt, puis lancer la vraie tâche

Le test de prompt permet d’itérer rapidement avec une réponse en streaming. Run now utilise ensuite le même runner que la planification Windows.

  1. Dans Tasks, sélectionnez une tâche.

    Cliquez sur Prompt.

  2. Modifiez le texte dans Agent prompt.

    Précisez le résultat attendu, le format et les limites. Exemple : longueur maximale, langue, rubriques obligatoires.

  3. Cliquez sur Save prompt.

    Le texte est enregistré dans la définition de la tâche.

  4. Lancez Test the prompt.

    La réponse apparaît progressivement dans Streamed agent output. Le test utilise la liste blanche d’outils de la tâche.

  5. Ajustez et recommencez si nécessaire.

    Utilisez Cancel pour interrompre une génération trop longue.

  6. Revenez à Tasks et cliquez sur Run now.

    Si un workflow existe, il est prioritaire. Sans workflow, le runner exécute le prompt avec les outils autorisés.

Test de prompt ≠ test du workflow. Le bouton Test the prompt teste l’agent et la liste blanche. Run now exécute le chemin réel de la tâche et crée le rapport normal.

Scénario guidé 04

Connecter Gmail et Google Calendar

L’autorisation Google est interactive et doit être réalisée dans l’interface sous le même compte Windows que celui qui exécutera les tâches planifiées.

Préparer Google Cloud

  1. Créez ou sélectionnez un projet Google Cloud.

    Activez Gmail API et Google Calendar API.

  2. Configurez l’écran de consentement OAuth.

    Ajoutez votre compte comme utilisateur de test tant que l’application reste en mode test.

  3. Créez un client OAuth de type Desktop app.

    Copiez le Client ID et le Client Secret.

  4. Fermez OD.MyLocalAgent et complétez settings.json.

    Conservez les autres sections du fichier et ajoutez ou mettez à jour la section suivante.

{
  "Google": {
    "ClientId": "YOUR_DESKTOP_CLIENT_ID",
    "ClientSecret": "YOUR_DESKTOP_CLIENT_SECRET"
  }
}

Le fichier se trouve dans %LOCALAPPDATA%\OD.MyLocalAgent\settings.json.

Autoriser dans l’application

  1. Relancez l’application et ouvrez Tools.

    La section Google Workspace doit indiquer que la configuration OAuth est disponible.

  2. Cliquez sur Connect.

    Terminez le consentement dans le navigateur avec le compte Google voulu.

  3. Revenez dans l’application et actualisez le statut.

    Utilisez Refresh status si nécessaire.

  4. Testez Gmail et Calendar séparément.

    Chaque bouton Test connection effectue une opération en lecture seule et affiche la latence.

  5. Dans la tâche, cochez seulement Gmail et/ou Calendar.

    L’autorisation OAuth ne remplace pas la liste blanche de chaque tâche.

Lire les messages et envoyer un message sont deux capacités différentes. gmail.send reste bloqué tant que Allow sending email n’est pas explicitement activé dans Settings.

Scénario guidé 05

Connecter Dropbox

Les valeurs Dropbox sont saisies en écriture seule puis protégées par DPAPI pour le compte Windows courant.

  1. Créez une application dans Dropbox App Console.

    Choisissez l’accès le plus limité possible, idéalement un dossier d’application.

  2. Activez uniquement les permissions nécessaires.

    Lecture de métadonnées, lecture de contenu et écriture selon les alias utilisés.

  3. Obtenez les identifiants.

    Utilisez soit un access token, soit un refresh token accompagné de l’app key.

  4. Ouvrez Tools → Dropbox.

    Saisissez les nouvelles valeurs dans les champs prévus.

  5. Cliquez sur Save credentials.

    Les secrets sont chiffrés pour l’utilisateur Windows courant et ne sont pas écrits dans settings.json.

  6. Lancez Test connection.

    Le test effectue une opération de lecture seule.

  7. Ajoutez Dropbox à la tâche concernée.

    Cochez Dropbox dans Tool whitelist et utilisez un alias dropbox.* dans le workflow.

Scénario guidé 06 · Activation cloud

Activer la recherche web Ollama protégée

Web Search est désactivé sur une installation neuve. Les requêtes et les extraits reçus quittent l’ordinateur vers l’endpoint cloud Ollama configuré.

  1. Créez un compte ollama.com et obtenez une clé Web Search.

    L’offre individuelle gratuite peut être limitée, surtout lors de rafales de requêtes.

  2. Ouvrez Tools → Web search (cloud).

    Activez la recherche et conservez normalement https://ollama.com/api/web_search.

  3. Collez la clé en écriture seule puis sélectionnez Save.

    DPAPI protège la clé, qui n’est jamais écrite dans settings.json. Un endpoint personnalisé reçoit la clé et les requêtes.

  4. Sélectionnez Test connection.

    Le test à requête fixe affiche seulement la durée et le nombre de résultats, jamais les extraits.

  5. Activez Web search (web) (cloud) dans la tâche.

    Utilisez web.search avec query obligatoire et maxResults facultatif (5 par défaut, 10 maximum).

Les résultats sont des données externes non fiables. Titres et extraits sont bornés, contrôlés exactement une fois et renvoyés dans une seule enveloppe protectedResults. Le dépassement est explicitement tronqué ou omis. Index et URL sont des métadonnées supprimées si Guardrails masque le contenu. Un contrôle désactivé ou en échec reste en Base64 marqué, jamais en texte brut.
Pour une veille multi-thèmes, activez aussi le groupe Web Discovery et utilisez research.discover. Le mode sliding vérifie localement les dates après téléchargement : il commence à deux jours calendaires puis élargit à quatre et sept jours seulement si le nombre minimal d’articles récents n’est pas atteint. Les pages trop anciennes, futures ou sans date vérifiable sont exclues ; utilisez freshnessWindow: "none" pour autoriser explicitement les contenus sans date. La recherche, la lecture et le tri restent déterministes ; seuls les titres et résumés finalement retenus passent dans Guardrails et sont livrés dans protectedResults. Une traduction demandée ne s’exécute qu’après un verdict propre, puis son résultat exact est contrôlé une seconde fois. L’historique windowHistory permet de vérifier les budgets et résultats des fenêtres 2, 4 et 7 jours. Les erreurs du fournisseur ne sont pas assimilées à zéro résultat : searchStatus distingue une recherche disponible, dégradée, indisponible ou limitée. Un HTTP 429 arrête les requêtes restantes et produit un diagnostic indiquant que la disponibilité des sources n’a pas pu être déterminée. Les exemples éditoriaux n’inventent rien en cas de pénurie : zéro candidat produit zéro post LinkedIn et aucun article du dimanche. Une source suffit à un article focalisé, deux à une analyse croisée limitée, et trois ou plus à un article multi-source.

Scénario guidé 07

Explorer un prompt dans l’AI playground

Le playground sert aux essais libres. Son mode par défaut appelle directement le fournisseur ; les outils et les skills demandent chacun une autorisation explicite.

  1. Ouvrez AI playground.

    Le badge en haut indique le fournisseur, le modèle et la politique globale effective utilisée par cette génération.

  2. Cliquez sur Check health.

    Résolvez d’abord un endpoint ou un modèle indisponible.

  3. Saisissez un prompt.

    Sans case cochée, la réponse est une complétion brute, sans outil ni skill.

  4. Choisissez les capacités nécessaires.

    Cochez Allow Tools et/ou Allow Skills seulement si le test l’exige.

  5. Cliquez sur Generate.

    La réponse apparaît progressivement. Cancel interrompt la génération.

Allow Tools Allow Skills Mode obtenu
NonNonComplétion brute du fournisseur.
OuiNonAgent avec tous les groupes d’outils installés et autorisables.
NonOuiAgent avec summarize, extract action items et classify email.
OuiOuiAgent avec outils et skills intégrés.
Allow Tools donne accès à tous les groupes dans ce test interactif, mais les garde-fous globaux restent actifs : sandbox fichiers, hôtes HTTP autorisés et options Safety.

Conversation persistante

Converser avec Direct Chat

Direct Chat conserve plusieurs conversations locales et envoie leur contexte au fournisseur actif. Il démarre sans outil ; vous pouvez activer des outils explicitement pour une conversation donnée.

  1. Ouvrez Direct Chat, juste après Tasks.

    Une conversation New chat est créée automatiquement si aucun historique n’existe.

  2. Saisissez votre message.

    Cliquez sur Send ou utilisez Ctrl+Entrée. Une seule réponse peut être générée à la fois. Après l’envoi, la zone est volontairement vidée : Send redevient disponible dès que vous saisissez un nouveau message ou ajoutez une pièce jointe.

  3. Ajoutez une pièce jointe si nécessaire.

    Les fichiers texte, PDF, Word et Excel sont lus localement dans des limites contrôlées. Les images PNG, JPEG, WebP, GIF et BMP sont transmises comme images et exigent un modèle compatible vision. Le contenu de la pièce jointe est conservé avec le message afin de restaurer le contexte lors de la réouverture de la conversation.

  4. Générez une image ou un audio seulement si l’action est proposée.

    Generate image et Generate audio apparaissent uniquement lorsque le fournisseur actif déclare explicitement la capacité. L’image offre un aperçu, une ouverture en taille réelle et une sauvegarde. L’audio WAV offre lecture, arrêt, durée lorsqu’elle est disponible et sauvegarde. Les contenus cloud sont signalés.

  5. Activez l’agent seulement lorsque c’est utile.

    Sous la liste des conversations, ouvrez Tools & permissions, cochez Enable tools for this conversation, sélectionnez les groupes d’outils et les permissions sensibles nécessaires, puis cliquez sur Save permissions. Tout est désactivé par défaut. Pour File system, ajoutez chaque dossier nécessaire dans Authorized locations et choisissez l’accès lecture seule ou lecture/écriture. La liste des permissions défile indépendamment ; les mêmes sandbox, Guardrails et règles de connecteurs que pour une tâche restent applicables.

  6. Transformez un échange utile en tâche.

    Create task reprend le dernier prompt utilisateur et les autorisations de cette conversation dans une tâche désactivée, puis ouvre son éditeur. L’historique et les pièces jointes ne sont pas copiés : complétez la fréquence et vérifiez la tâche avant de l’activer.

  7. Suivez la réponse en streaming.

    Cancel interrompt la génération. Une réponse interrompue reste identifiée comme annulée ; après un arrêt brutal, une réponse inachevée est marquée en échec au prochain démarrage. Une erreur du fournisseur ou un flux incomplet est aussi marqué Failed et reçoit un identifiant de corrélation d’incident ; vous pouvez poursuivre la conversation après cet échec.

  8. Retrouvez ou créez une conversation.

    La colonne gauche trie les conversations par activité récente. New chat démarre un nouvel échange et Load older messages charge une page antérieure. Faites glisser le séparateur entre la liste et la conversation lorsque vous avez besoin de plus de place pour les chemins de dossiers autorisés.

  9. Copiez un message si nécessaire.

    Sélectionnez l’icône de copie d’une bulle pour placer son texte dans le presse-papiers Windows.

  10. Supprimez uniquement après vérification.

    Delete conversation demande confirmation puis efface définitivement la conversation, ses messages et tous les médias associés.

Lorsque l’historique approche de la fenêtre de contexte déclarée, Direct Chat résume les anciens tours et garde au moins les quatre derniers tours utilisateur en texte intégral. Le résumé réduit seulement le contexte envoyé au modèle : tous les messages originaux restent dans la base et dans l’interface.
Les conversations sont enregistrées en clair dans <FileSystem:RootPath>\.od-my-local-agent\data\direct-chat.db. Cette base SQLite dédiée n’est pas le SQLite Tool, n’est pas accessible aux workflows et n’est pas protégée par DPAPI. Avec un fournisseur cloud, le contexte utile est envoyé à l’endpoint configuré. Les médias sont limités par défaut à 25 Mio chacun et 250 Mio par conversation. Ils ne sont jamais copiés automatiquement lors de la création d’une tâche.

Scénario guidé 07

Tester un outil isolément

Tool tester exécute un alias précis avec des arguments JSON explicites. C’est le moyen le plus direct de vérifier une connexion ou un garde-fou.

  1. Ouvrez Tool tester.

    Sélectionnez un alias dans la liste.

  2. Lisez l’indication des arguments.

    Le formulaire rappelle les noms attendus par l’alias.

  3. Saisissez un objet JSON.

    Pour lister la racine de la sandbox, choisissez filesystem.list et utilisez l’exemple ci-dessous.

{
  "path": "."
}
  1. Cliquez sur Run tool.

    Le résultat formaté et la durée s’affichent à droite.

  2. En cas de blocage, lisez le nom du réglage.

    Une opération protégée indique précisément l’option Safety requise. N’activez cette option qu’après vérification.

Commencez par des alias sans effet de bord : filesystem.list, filesystem.read, gmail.readUnread, calendar.today ou dropbox.list.

Scénario guidé 08

Activer un fournisseur OpenAI-compatible

Le cloud est un choix explicite. Dès qu’il est sélectionné, les prompts et le contexte utile sont envoyés à l’endpoint configuré.

  1. Ouvrez Settings → AI provider.

    Sélectionnez OpenAI-compatible (cloud, opt-in) dans Active provider, à droite de Test connection. Les réglages Ollama restent mémorisés : vous pourrez revenir à Ollama sans les ressaisir.

  2. Vérifiez l’avertissement cloud.

    Assurez-vous que la politique de confidentialité de l’endpoint convient aux données traitées.

  3. Renseignez Endpoint, Model et Timeout.

    Pour OpenAI, l’endpoint par défaut est https://api.openai.com/v1. Un serveur compatible peut utiliser une autre URL. Pour OpenRouter, utilisez https://openrouter.ai/api/v1 et recopiez l’identifiant exact du modèle, suffixe :free compris s’il est affiché.

  4. Chargez la liste si le fournisseur la propose.

    Refresh OpenAI-compatible models récupère les modèles exposés par l’endpoint. La liste reste modifiable : saisissez l’identifiant manuellement si votre fournisseur ne publie pas son catalogue ou si vous connaissez déjà le nom voulu.

  5. Saisissez la clé dans Replace API key.

    Le champ reste vide après sauvegarde : la clé est écrite dans le magasin DPAPI, jamais réaffichée.

  6. Cliquez sur Save settings.

    Le fournisseur s’applique aux prochains tests et exécutions, sans redémarrage.

  7. Lancez Test connection.

    Le test vérifie le fournisseur actuellement coché, l’endpoint et la présence du modèle dans son catalogue. Une erreur de clé, d’endpoint ou de modèle est affichée comme telle ; aucun retour silencieux vers Ollama n’a lieu. Un code 404 OpenRouter provenait historiquement d’une route de détail de modèle non prise en charge ; le test utilise désormais le catalogue standard.

La clé API ne doit jamais être ajoutée manuellement à appsettings.json ou settings.json. Utilisez exclusivement le champ protégé de l’application.

Dashboard

Nombre de tâches, état du fournisseur, prochaines exécutions, historique récent et actions rapides.

Référence

Tâches, prompts et workflows

Comprendre la différence entre prompt et workflow, régler la génération et utiliser les éditeurs assistés avant d’aborder les formats de référence.

Prompt seul

L’agent interprète l’objectif et peut choisir parmi les outils autorisés. Ce mode est souple, mais le comportement de tool-calling dépend du modèle.

Workflow

Les étapes suivent l’ordre défini par défaut ; une décision peut choisir une autre branche validée. C’est le mode recommandé pour les automatisations sans surveillance. Si prompt et workflow coexistent, le workflow est prioritaire.

Orienter un workflow avec une décision

Le Stage 29 permet à une étape flow.decision de choisir la suite sans demander au modèle d’exécuter lui-même le routage. Le test peut porter sur un texte, un nombre ou une propriété d’un objet JSON. Si le test est vrai, le workflow rejoint target ; s’il est faux, il rejoint next ou poursuit avec l’étape suivante. 

[
  {
    "step": "flow.decision",
    "args": {
      "source": "{{classification.output}}",
      "path": "score",
      "operator": "greaterThanOrEqual",
      "value": 0.8,
      "target": "automaticReply",
      "fallback": "manualReview"
    },
    "next": "manualReview"
  },
  { "step": "ai.prompt", "id": "automaticReply",
    "args": { "prompt": "Prepare an answer." }, "next": "@end" },
  { "step": "ai.prompt", "id": "manualReview",
    "args": { "prompt": "Prepare a review note." } }
]

fallback est utilisé uniquement lorsque le test ne peut pas être effectué, par exemple si la source n’est pas un JSON valide, si une propriété demandée par un opérateur autre que exists manque ou si son type est incompatible. Le workflow est refusé avant sauvegarde si une destination n’existe pas, si une étape est inaccessible ou si les routes forment une boucle.

Obtenir un objet JSON depuis ai.prompt

Ajoutez responseSchema à une étape ai.prompt pour demander une réponse objet vérifiable. Le fournisseur reçoit le schéma et MyLocalAgent vérifie de nouveau le JSON avant de rendre la sortie disponible au workflow. Vous pouvez ensuite tester directement une propriété avec {{classification.output.category}} ou avec une décision et son argument path. 

{
  "step": "ai.prompt",
  "id": "classification",
  "args": { "prompt": "Classify: {{task.prompt}}" },
  "responseSchema": {
    "type": "object",
    "properties": {
      "category": { "type": "string" },
      "score": { "type": "number" }
    },
    "required": ["category", "score"],
    "additionalProperties": false
  }
}
Dans ce premier lot, une étape ai.prompt avec responseSchema ne peut pas aussi déclarer toolAliases. Si la réponse n’est pas un JSON strict ou ne respecte pas le schéma, l’étape échoue selon sa politique d’erreur.

Réglages de génération hiérarchiques

Settings définit Temperature, Top P et Context window pour tous les nouveaux appels. Une tâche peut remplacer indépendamment Temperature et/ou Top P avec AI generation override. Une étape IA en forme objet peut à nouveau remplacer chaque propriété. La résolution est indépendante : étape IA → tâche → Settings. Context window reste global et n’apparaît jamais dans le JSON d’une tâche ou d’une étape. 

{
  "generationOptions": {
    "temperature": 0.1
  },
  "workflow": [
    {
      "step": "ai.summarize",
      "id": "summary",
      "generationOptions": {
        "topP": 0.9
      }
    }
  ]
}

Dans cet exemple, l’étape utilise Temperature 0.1 depuis la tâche et Top P 0.9 depuis l’étape. Les cases Use global default de l’éditeur sont indépendantes et affichent la valeur effective ainsi que sa provenance. Une valeur invalide désactive la sauvegarde. L’éditeur de prompt affiche et utilise ces valeurs effectives, y compris les modifications non encore sauvegardées, lorsqu’il exécute Test.

generationOptions est refusé sur une étape non IA. Les champs inconnus, les valeurs nulles ou hors plage, ainsi que context, fournisseur, endpoint et secrets sont refusés. Une tâche ancienne sans override reste valide ; un objet vide est supprimé lors de la sauvegarde canonique.

File globale d’exécution du modèle

Dans Settings → AI provider, le réglage Maximum simultaneous model requests limite les appels simultanés provenant de l’application et de tous les Runners actifs. Sa valeur par défaut est 1, recommandée pour Ollama local. Augmentez-la uniquement si le modèle sélectionné et le GPU gèrent correctement les générations parallèles. Une demande attend son créneau sans consommer le délai du fournisseur, et son attente peut être annulée.

Sélection ponctuelle du modèle et préchauffage

Ajoutez "model": "nom-du-modèle" à une tâche pour choisir un modèle du fournisseur actif pendant cette tâche uniquement. Vous pouvez aussi l’ajouter à une étape objet ai.prompt : cette valeur est alors prioritaire et ne s’applique qu’à cette étape. Elle ne modifie jamais le modèle défini dans Settings et le modèle par défaut est restauré, y compris après une erreur ou une annulation. 

{
  "model": "qwen3:32b",
  "workflow": [
    {
      "step": "ai.prompt",
      "id": "review",
      "args": { "prompt": "Review {{draft.output}}." },
      "model": "qwen3:32b"
    }
  ]
}

Avec Ollama, le modèle temporaire est chargé et vérifié par un court tour de chauffe juste avant son exécution. Il doit donc être installé localement ; sinon la tâche ou l’étape échoue sans modifier la configuration. Le champ model doit être une chaîne non vide et n’est admis au niveau d’une étape que pour ai.prompt. Les placeholders {{ModelName}} et {{ModelInfo}} indiquent le modèle effectivement sélectionné.

Limites du modèle. Temperature et Top P peuvent avoir un effet légèrement différent selon le fournisseur et le modèle. Modifier les deux simultanément rend le résultat plus difficile à prévoir, et davantage d’aléa peut réduire la fiabilité du JSON structuré ou du choix d’outils. La tokenisation du fournisseur reste prioritaire : Context window est un budget déclaré, pas un compteur exact universel, et ne peut pas augmenter la capacité physique du modèle.

AI Workflow Helper

AI Helper transforme une description en anglais en exactement le tableau de workflow affiché dans l’éditeur. Un workflow chargé devient localement une description déterministe et modifiable, sans appel au modèle. Vous pouvez la modifier ou fournir une instruction de raffinement à usage unique ; aucun historique de chat n’est conservé. La réponse est diffusée par le fournisseur choisi dans Settings et doit passer la validation stricte de l’application. La génération, le raffinement et leurs réparations utilisent toujours Temperature 0 / Top P 1, avec le Context window global.

Examinez chaque proposition de groupe d’outils ou de dossier absolu : elle est décochée par défaut et doit être acceptée explicitement. Les chemins dynamiques produisent un avertissement sans autorisation inventée ; les réglages Safety restent globaux et ne sont jamais modifiés. Apply met à jour ensemble le JSON, les outils et les emplacements ; seul Save task persiste ces valeurs. Undo assisted change est l’unique annulation à un niveau partagée par l’AI Helper, le Tool catalog et le Workflow prompt editor : elle restaure d’un seul geste le JSON, les outils et les emplacements précédents, jusqu’à la sauvegarde, au rechargement, à la navigation ou à une application assistée ultérieure.

AI Explain valide d’abord le workflow localement, puis explique les étapes, prompts, skills, placeholders, flux de données, autorisations, barrières Safety, effets et échecs probables. Text est le mode de repli fiable. Rendered Markdown réutilise la même réponse dans un document WebView2 restreint ; si le runtime manque, Text reste disponible et seul un lien explicite vers la page Microsoft officielle est proposé. Toute la fenêtre, y compris le rendu Markdown, suit le thème clair ou sombre actuellement sélectionné. L’explication et ses réparations utilisent également la politique interne fixe Temperature 0 / Top P 1. L’explication décrit néanmoins les overrides configurés et leur provenance effective.

Confidentialité et limites. L’assistant n’exécute aucune étape, n’appelle aucun outil ou skill, ne lit aucun fichier référencé, ne change aucun réglage Safety et ne persiste pas son contenu. Le fournisseur cloud reçoit la description et le contexte du workflow lorsqu’il est sélectionné. Un JSON valide peut rester incorrect sémantiquement et l’analyse statique ne prévoit pas tous les chemins ou valeurs d’exécution. Cancel conserve la sortie partielle, sans permettre Apply.

Tool catalog

Tool catalog est une référence consultable de tous les alias du Tool Map, groupés par groupe d’outils, avec leur description, leurs arguments typés, les indicateurs requis/optionnel, les exemples, les valeurs autorisées et un onglet de placeholders. La fenêtre est entièrement déterministe : elle n’appelle aucun modèle, aucun outil, aucun fichier et aucun réseau. Sélectionner une entrée affiche l’aperçu exact du snippet qui sera inséré.

Insert insère et garde la fenêtre ouverte, ce qui permet d’accumuler plusieurs étapes dans une même session ; Insert and close insère puis ferme ; Close ne renvoie le résultat accumulé que si au moins une modification effective existe ; Cancel abandonne toute la session. Fermer avec des insertions en attente demande confirmation.

Les commandes Insert et Insert and close ne concernent que l’onglet Steps et sont donc masquées sur l’onglet Placeholders, où un placeholder se récupère uniquement avec Copy vers le presse-papiers. Sur cet onglet, Close est la seule sortie conservant les insertions déjà accumulées.

Le curseur détermine la position : à l’intérieur d’un élément l’insertion se fait après celui-ci, entre deux éléments après celui de gauche, avant le premier à l’index 0, après le dernier en ajout final. Si le JSON n’est pas analysable, le snippet est tout de même inséré tel quel au curseur, avec l’indentation de la ligne et un avertissement explicite indiquant que les séparateurs doivent être corrigés à la main.

Autorisations. Une étape dont le groupe d’outils n’est pas dans la liste blanche de la tâche produit un avertissement et une case d’acceptation décochée que vous devez valider explicitement. Le groupe intégré ai n’est qu’une étiquette de regroupement : il n’est jamais autorisable et n’apparaît jamais dans un résultat d’acceptation. Les capacités requises sont signalées mais ne sont jamais accordées automatiquement.

Workflow prompt editor

Edit workflow text liste dans l’ordre les arguments texte éligibles déjà présents dans le workflow, notamment ai.prompt.prompt, filesystem.write.content et filesystem.powerShell.script. Les valeurs courtes ou contraintes par un format sont exclues. Il modifie uniquement le texte choisi. Aucune étape n’est ajoutée, supprimée, réordonnée, renommée ni retypée ; aucun id, politique d’erreur, tentative, option de génération ou autre argument n’est touché. Les étapes sont identifiées par leur position, si bien que des ids dupliqués restent sans ambiguïté.

Pour une entrée ai.prompt, le champ Model override (empty = task or Settings) permet de choisir un modèle spécifique à cette étape. Dans l’éditeur de tâche, décochez Use model from Settings et renseignez Task model override pour appliquer un modèle à toute la tâche. La priorité est : modèle de l’étape ai.prompt, puis modèle de la tâche, puis modèle de Settings. Ce choix ne change jamais de fournisseur : le fournisseur actif reste celui de Settings.

Les prompts s’écrivent avec de vrais retours à la ligne. Le texte de travail est canonique LF : les CRLF et CR isolés sont normalisés en LF et signalés, et rien d’autre dans vos espaces n’est modifié. Comme les retours à la ligne sont écrits en échappements \n, chaque prompt occupe toujours une seule ligne physique du JSON, et un aller-retour sans modification est sans perte. Chaque ligne de la liste affiche un aperçu sur une ligne où les sauts de ligne et tabulations deviennent des marqueurs visibles.

includeContext est une option indépendante, activée par défaut sur une nouvelle étape ai.prompt. Elle n’est jamais pilotée par l’option générique d’arguments optionnels. Vous pouvez délibérément la désactiver et référencer un unique placeholder de sortie antérieure pour n’envoyer que des données choisies. Si un prompt référence déjà une sortie antérieure ou le contexte accumulé alors que includeContext est actif, un avertissement de duplication apparaît : il est informatif, ne modifie automatiquement aucune valeur et ne bloque pas Apply.

Plusieurs prompts peuvent être modifiés dans une même session. Apply valide l’ensemble, écrit toutes les modifications en une fois et ferme ; il n’est actif que si une modification effective existe et qu’aucun prompt n’est vide. Revert step restaure une seule entrée et Cancel abandonne la session. Cette fenêtre n’a volontairement pas de commande Close, et la fermer avec des modifications en attente demande confirmation.

Prompts non vides et reformatage. Un prompt d’ai.prompt absent, nul, non textuel, vide ou composé uniquement d’espaces est refusé partout : Save, Validate, validation de l’AI Helper et Apply de l’éditeur de prompts. Chaque insertion structurée ou application de prompt réussie resérialise le tableau au format canonique : un formatage manuel du workflow est donc normalisé. Le JSON, les prompts, les valeurs d’arguments et les chemins ne sont jamais journalisés ni persistés par ces fenêtres.

Structure d’une tâche

Le format d’une tâche regroupe son identité, sa planification, ses autorisations, ses réglages et son workflow éventuel.

Forme d’une tâche

{
  "id": "daily-mail-summary",
  "name": "Daily mail summary",
  "schedule": "0 7 * * *",
  "prompt": "Summarize today's important messages.",
  "tools": ["gmail", "filesystem"],
  "fileSystemAccess": [],
  "generationOptions": {
    "temperature": 0.1
  },
  "workflow": [
    "gmail.readToday",
    {
      "step": "ai.summarize",
      "id": "summary",
      "generationOptions": {
        "topP": 0.9
      }
    },
    {
      "step": "filesystem.write",
      "args": {
        "path": "reports/mail-summary.md",
        "content": "{{summary.output.text}}"
      }
    }
  ],
  "enabled": true,
  "errorPolicy": "StopOnError"
}

Règles importantes

  • L’id suit le format [a-z0-9-]+ et devient immuable après création.
  • Le prompt peut être vide uniquement si le workflow contient au moins une étape.
  • Un alias d’outil exige que son groupe soit coché dans Tool whitelist.
  • Un skill ai.* est toujours autorisé dans un workflow.
  • Les chemins relatifs restent sous le RootPath configuré.
  • Un chemin absolu exige un emplacement autorisé appartenant à la tâche.

Emplacements autorisés

L’éditeur permet d’autoriser pour cette tâche des dossiers absolus supplémentaires, sans créer de catalogue global. Chaque règle inclut ses sous-dossiers et accorde ReadOnly ou ReadWrite. Une liste vide n’autorise aucun chemin absolu. Les droits Windows restent prioritaires. 

"fileSystemAccess": [
  {
    "path": "D:\\Production\\Incoming",
    "access": "ReadOnly"
  },
  {
    "path": "E:\\Archives\\Daily",
    "access": "ReadWrite"
  }
]

Cette section rassemble les marqueurs disponibles, leur portée, leur syntaxe et les règles de résolution dans les prompts et workflows.

Placeholders du prompt agentique (tâches sans workflow)

Pour une tâche enregistrée dont le workflow est vide, MyLocalAgent remplace exactement {{Today}}, {{Now}}, {{task.id}} et {{task.name}} avant que le prompt atteigne le modèle. Cela s’applique à run planifié/CLI, Run now, test-prompt et Test the prompt dans l’éditeur, y compris au texte courant non sauvegardé. La date et l’heure proviennent d’un unique instantané de l’horloge Windows locale injectée, pris au moment de l’exécution.

Marqueur inconnu : conservé avec un warning

Create a greeting for {{customer_name}}.

MyLocalAgent envoie {{customer_name}} sans modification et continue avec un warning non bloquant. Le modèle peut interpréter ce texte non résolu de manière imprévisible ; la conservation décrit uniquement ce que l’application a envoyé. Les warnings durables contiennent un code applicatif, des catégories et des compteurs agrégés, jamais le marqueur brut, le prompt, le nom de tâche, la valeur remplacée ou le chemin produit.

{{previous.output}} appartient aux workflows

Summarize {{previous.output}}.

Dans une tâche sans workflow, ce marqueur reste inchangé avec un warning workflow-only. Le concept équivalent valide est un workflow ordonné dans lequel une étape précédente a produit une sortie : 

[
  "gmail.readToday",
  {
    "step": "ai.prompt",
    "args": { "prompt": "Summarize {{previous.output}}." }
  }
]

La sauvegarde stocke le modèle original, l’enregistrement du planning le laisse également intact, et seule l’exécution fournit l’identité, la date et l’heure locales. La substitution se fait en une seule passe, sans récursion : si le nom enregistré de la tâche contient lui-même {{Today}}, ce texte inséré reste littéral. Un chemin de fichier résolu exige toujours le groupe d’outils de la tâche, une autorisation read-write correspondante, les droits Windows et tout réglage Safety indépendant. Une expansion réussie est indépendante du choix d’un outil par le modèle et de la réussite de cet outil.

Les workflows conservent le jeu plus large de placeholders porteurs de données présenté ci-dessous et leur comportement d’échec strict. Une tâche avec un workflow non vide ne pré-résout pas son prompt enregistré. AI Playground, Tool tester, AI Workflow Helper/Explain, Guardrails, skills, ai.prompt de workflow et les autres surfaces sans tâche ne reçoivent pas cette expansion de date, d’identité ou de contexte de workflow.

Placeholders d’information du modèle (toutes les surfaces)

Les quatre placeholders suivants sont disponibles dans les tâches planifiées, Run now, les tests de prompt, les tâches agentiques, toutes les valeurs chaîne d’un workflow et AI Playground, en mode brut comme en mode agent. MyLocalAgent les remplace avant l’appel au modèle ou à l’outil de workflow.

{{ModelName}}qwen3:14b
{{ModelSettings}}Temp 0.25 - TopP 0.9
{{ModelContextSize}}32768
{{ModelInfo}}ModelName qwen3:14b - Temp 0.25 - TopP 0.9 - Context 32768

Temperature et Top P sont les valeurs effectives de l’appel : une surcharge d’étape IA gagne sur celle de la tâche, qui gagne sur Settings. Une étape d’outil sans appel IA utilise les valeurs effectives de la tâche ; AI Playground utilise Settings. La taille de contexte est la fenêtre déclarée dans Settings, pas le nombre de tokens consommés, la place restante ni une limite de sortie. Les nombres utilisent un format invariant sans séparateur de milliers. 

Prompt : Generate a short diagnostic headed "{{ModelInfo}}".

Valeur envoyée avec les réglages d’exemple :
Generate a short diagnostic headed "ModelName qwen3:14b - Temp 0.25 - TopP 0.9 - Context 32768".

La substitution est insensible à la casse, se fait en une seule passe et n’analyse jamais à nouveau le nom du modèle inséré. Le premier élément visible de chaque log de tâche conservé est la valeur {{ModelInfo}} au niveau de la tâche. Une étape IA de workflow peut ensuite utiliser ses propres surcharges. Cette ligne de log contient uniquement le nom du modèle, Temperature, Top P et le contexte déclaré ; elle n’ajoute ni prompt, sortie, chemin, donnée externe, endpoint ou secret au log.

Étapes, sorties et placeholders de workflow

Une étape sous forme de chaîne ne prend aucun argument. La forme objet accepte step, id, args, la répétition facultative forEach et une politique d’erreur. Les placeholders sont remplacés juste avant l’exécution de l’étape.

{{task.name}}Nom de la tâche.
{{task.prompt}}Prompt enregistré.
{{previous.output}}Sortie de l’étape précédente.
{{stepId.output}}Sortie d’une étape désignée par son id.
{{stepId.output.property}}Propriété extraite d’une sortie JSON ; les index de tableau comme items[0].name sont acceptés.
{{workflow.context}}Instantané JSON de toutes les sorties réussies accumulées jusque-là.
{{foreach.item}}Élément courant, uniquement dans une étape qui déclare forEach. Les sélecteurs structurés comme {{foreach.item.subject}} sont acceptés.

Les délimiteurs sont exactement deux accolades ouvrantes et deux accolades fermantes : {{placeholder}}. Un placeholder peut être seul ou entouré de texte dans toute valeur chaîne située sous args. La résolution parcourt les objets et tableaux, mais ne modifie ni les noms de propriétés JSON, ni les nombres, ni les booléens. Les noms et propriétés JSON sélectionnées ne sont pas sensibles à la casse. Il n’existe pas d’échappement pour écrire littéralement {{...}} : toute séquence de ce type est interprétée et un nom inconnu fait échouer l’étape.

Les sélecteurs structurés commencent après .output. Un point sélectionne une propriété d’objet et [0] un élément de tableau avec un index commençant à zéro. Par exemple, {{files.output.entries[0].name}} retourne le nom du premier fichier. Une propriété absente, un index invalide ou une sélection structurée appliquée à du texte simple fait échouer l’étape.

Les dates utilisent le fuseau Windows local. Les crochets contiennent un format personnalisé .NET. Pour les noms de fichiers, les alias YYYY, YY, DD et hh signifient yyyy, yy, dd et HH sur 24 heures. Évitez / et : dans un nom de fichier Windows. 

{
  "path": "reports/{{Today[YYYY]}}/triage-{{Now[yyyyMMdd-hhmmss]}}.md",
  "content": "{{triage.output.text}}"
}

SQLite

Le groupe sqlite fournit quatre alias pour un seul fichier de base local autorisé : sqlite.listObjects, sqlite.describeTable, sqlite.query et sqlite.execute. Ajoutez sqlite aux outils autorisés de la tâche. Les chemins relatifs restent sous FileSystem:RootPath ; un chemin absolu requiert une autorisation dans Authorized locations. Les trois premiers alias requièrent ReadOnly. sqlite.execute exige aussi ReadWrite et la capacité de tâche SqliteWrite.

Utilisez un chemin de base, jamais une chaîne de connexion, une URI, une base réseau ou :memory:. Une lecture ne crée jamais de fichier. Une écriture ne crée un fichier manquant qu’avec "createIfMissing": true. Query et execute acceptent exactement une instruction. N’utilisez ni transactions, ATTACH, PRAGMA, VACUUM, extensions ni objets internes sqlite_.

Les paramètres sont un objet JSON de scalaires nommés. Conservez le préfixe SQLite natif dans chaque clé (@, : ou $) ; les valeurs sont liées de manière sûre et ne doivent jamais être concaténées au SQL.

Préparer la tâche et les réglages

  1. Dans l’éditeur de tâche, cochez uniquement sqlite dans Tool whitelist.
  2. Pour les lectures, utilisez un chemin relatif sous FileSystem:RootPath ou accordez au fichier absolu une autorisation ReadOnly dans Authorized locations.
  3. Pour une écriture, accordez ReadWrite au même emplacement, puis accordez explicitement SqliteWrite dans Sensitive operation permissions. Ces trois conditions sont indépendantes.
  4. Dans Settings → SQLite, définissez le nombre de lignes par défaut et maximal, les limites de caractères de résultat et de SQL, la limite BLOB et le délai d’attente. Les limites tronquent la réponse ; elles ne garantissent pas un nombre total de lignes ou d’objets.

La case Protect SQLite read results with Guardrails de l’éditeur est enregistrée avec chaque tâche. Le réglage homonyme de Settings sert seulement de valeur initiale aux nouvelles tâches et aux essais sans tâche (Tool tester et AI Playground) ; modifier Settings ne change pas une tâche existante.

Les quatre alias

  • sqlite.listObjects — databasePath, objectType (All, Table, View, Index ou Trigger), namePattern (motif SQLite LIKE) et maxResults. Renvoie les objets de schéma visibles, dans un ordre stable, sans leur SQL brut.
  • sqlite.describeTable — databasePath et tableName exact. Renvoie les colonnes, clés étrangères et index de cette table ou vue ; les corps de déclencheurs ne sont jamais renvoyés.
  • sqlite.query — databasePath, une instruction de lecture dans sql, parameters et maxRows. Dans cette version, fournissez un chemin de base : storageSpaceId est réservé et ne doit pas être renseigné.
  • sqlite.execute — databasePath, une instruction de modification dans sql, parameters et createIfMissing. L’appel est exécuté dans une transaction possédée par l’application.

Les lectures doivent être productrices de résultats (SELECT, WITH, VALUES ou EXPLAIN). Les écritures acceptent notamment INSERT, UPDATE, DELETE, CREATE, ALTER et DROP, mais pas RETURNING. Un seul énoncé est autorisé, avec au plus un point-virgule final et des commentaires de fin. Les paramètres doivent correspondre exactement aux paramètres nommés du SQL ; les objets, tableaux, paramètres positionnels et valeurs non finies ne sont pas acceptés.

{
  "databasePath": "data/sample.db",
  "sql": "SELECT id, name FROM items WHERE id >= @minimumId ORDER BY id",
  "parameters": { "@minimumId": 1 },
  "maxRows": 25
}

Sélectionnez sqlite.query dans Tool tester et utilisez cet objet pour lire une base synthétique. Pour inspecter son schéma, sélectionnez plutôt sqlite.listObjects :

{
  "databasePath": "data/sample.db",
  "objectType": "Table",
  "namePattern": "item%",
  "maxResults": 25
}

Pour décrire une table :

{
  "databasePath": "data/sample.db",
  "tableName": "items"
}

Pour créer une base synthétique puis une table vide, activez d’abord les trois autorisations d’écriture ci-dessus et appelez sqlite.execute une seule fois avec :

{
  "databasePath": "data/sample.db",
  "sql": "CREATE TABLE items (id INTEGER PRIMARY KEY, name TEXT NOT NULL)",
  "createIfMissing": true
}

Un accusé d’écriture contient seulement rowsAffected, lastInsertRowId lorsqu’il est significatif, databaseCreated et committed ; il ne réaffiche ni SQL, ni paramètres, ni données de la base.

Lire les résultats et protéger les données

Les trois alias de lecture retournent une enveloppe avec data ou protectedData, jamais les deux, ainsi que contentEncoding, screened, sqliteGuardrailsEnabled, les champs de confiance, screeningChunkCount et resultCharacterCount. Pour une lecture propre, data contient le résultat logique. Une requête expose des columns ordonnées (name, ordinal, declaredType) et des rows sous forme de tableaux afin de préserver l’ordre et les noms de colonnes dupliqués. Les objets et descriptions signalent aussi leur troncature ; query fournit hasMoreRows, truncated et resultTruncated.

Les BLOB sont décrits par $type, byteLength, base64 et omitted. Quand la limite BLOB est nulle ou dépassée, le contenu Base64 est omis. Les résultats s’arrêtent aux limites d’objets ou de lignes, puis de taille complète ; les données absentes ne doivent donc pas être interprétées comme inexistantes.

Settings → SQLite contrôle les lignes par défaut et maximales, les caractères de résultat, octets BLOB, caractères SQL et le délai d’attente. Chaque tâche conserve son propre choix Protect SQLite read results with Guardrails ; le réglage des nouvelles tâches n’est copié qu’à leur création. Les résultats protégés par Guardrails sont protégés ou retenus si le filtrage ne peut pas se terminer de manière sûre. Avec un fournisseur OpenAI-compatible, ce filtrage peut envoyer le contenu borné de la base au fournisseur cloud configuré. Désactiver ce filtrage pour une tâche renvoie les données en clair au workflow ou au modèle suivant. Guardrails est probabiliste et le Base64 est une défense en profondeur, non une isolation ni un chiffrement.

SQLite ne fournit ici ni chiffrement, sauvegarde ou restauration, migration en lot, réglage automatique WAL, base distante ou réseau, ATTACH, extension ou transaction contrôlée par l’appelant. Le délai d’attente traite l’attente de verrou, pas une limite de calcul ; l’annulation du Runner interrompt l’opération native. Une instruction autorisée peut toujours modifier beaucoup de lignes ou d’objets : aucun filtrage SQL ne peut prouver l’intention métier. Commencez avec des données jetables et non sensibles.

Passer des arguments dans un workflow

Utilisez la forme objet d’une étape avec step et un objet args. Les noms des propriétés sont ceux de la référence détaillée, en camelCase, et les valeurs respectent la syntaxe JSON. Pour un alias sans argument, utilisez simplement sa forme texte "<alias>" : aucun objet args n’est transmis et le comportement par défaut de l’outil s’applique.

Exemple Gmail : période et limite explicites

[
  {
    "step": "gmail.readRecent",
    "id": "recentMessages",
    "args": { "daysBack": 2, "maxMessages": 15 }
  }
]

Cette étape lit les messages reçus depuis le début du jour local situé deux jours avant aujourd’hui, avec au plus quinze messages demandés à Gmail. À l’inverse, ["gmail.readToday"] n’envoie aucun paramètre et lit les messages reçus aujourd’hui, sans limite demandée ; une éventuelle limite Guardrails configurée reste signalée dans le résultat.

Exemple Calendar : sélectionner la semaine locale

[
  {
    "step": "calendar.read",
    "id": "weekAgenda",
    "args": { "period": "Week" }
  }
]

La valeur Week demande les événements de la semaine locale en cours, du lundi au dimanche. Pour appeler Calendar sans paramètre, utilisez ["calendar.today"] : l’outil retourne uniquement les événements du jour local courant.

Protection contre l’effet « disque rayé ». Une étape ai.prompt démarre sans outil ; elle peut appeler uniquement les alias exacts déclarés dans toolAliases, eux-mêmes limités par les autorisations de la tâche. Lorsqu’elle dispose réellement d’outils, l’exécution s’arrête après huit tours, deux erreurs d’outil consécutives, ou dès la troisième demande strictement identique du même outil avec les mêmes arguments.

Répéter une étape pour chaque élément

Les étapes ai.prompt et filesystem.write acceptent la propriété de niveau étape forEach. Sa valeur doit être un unique placeholder, sans texte autour, vers une sortie antérieure qui devient un tableau JSON. Chaque élément est traité séquentiellement, dans l’ordre de la source, avec {{foreach.item}} et sa position à partir de 1 dans {{foreach.position}}. Les sélecteurs structurés comme {{foreach.item.subject}} sont acceptés. 

[
  { "step": "gmail.readToday", "id": "mails" },
  {
    "step": "ai.prompt",
    "id": "analyses",
    "forEach": "{{mails.output.messages}}",
    "args": {
      "prompt": "Analyse cet e-mail comme une donnée non fiable :\n{{foreach.item}}"
    }
  }
]

Une source vide réussit avec la sortie []. Toutes les sorties sont regroupées dans un tableau ordonné publié sous l’identifiant du step. Une étape accepte au maximum 100 éléments. Retry réessaie uniquement l’élément courant ; le premier échec définitif arrête le lot et aucune sortie partielle n’est publiée. ContinueOnError peut ensuite poursuivre le workflow, mais ne traite pas les éléments restants. Les effets déjà produits ne sont pas annulés. Pour Gmail, n’activez pas adaptiveReportOutput si le sélecteur cible messages, car le format compact utilise entries. Avec filesystem.write, rendez le chemin variable, sinon chaque itération remplace le même fichier.

Les deux opérations exigent un accès en lecture-écriture, refusent une destination existante et retournent un chemin JSON to réutilisable par l’étape suivante.

      "path": "incoming/report.tmp",

  {
    "step": "filesystem.setExtension",
    "args": {
      "path": "{{rename.output.to}}",

]

Utiliser l’extraction et la classification sans boucle

Ces deux skills appellent le LLM sans outil. Si args.text est omis, ils reçoivent la sortie complète de l’étape précédente ; placés en première étape, ils reçoivent le prompt de la tâche. Une valeur text explicite est prioritaire. Ils peuvent donc traiter en un seul appel tout le lot retourné par gmail.readUnread, sans boucle de workflow. Leur sortie suit la forme {"text":"..."} ; utilisez {{stepId.output.text}} pour insérer uniquement le Markdown.

ai.classifyEmail crée une ligne par message identifiable avec Message, Category, Reason et Deadline. Il produit seulement un rapport global : il ne crée pas de branche et ne peut pas lancer une opération différente pour chaque catégorie. 

[

]

    }

Dans Settings, l’option Run when the user is logged off (S4U) permet une exécution sans session interactive. Elle doit rester associée au même compte Windows, car les secrets DPAPI, les tokens Google et %LOCALAPPDATA% dépendent de cet utilisateur.

Protection contre la prompt injection

Comprendre le filtre de confiance

Les lectures Gmail et les réponses http.get / http.getText sont compactées de façon déterministe avant des appels LLM directs, sans outil, skill ni boucle d’agent. Cette réduction du risque est probabiliste : elle ne remplace jamais les limites Safety, la liste blanche d’outils, le bac à sable fichiers ou la liste d’hôtes HTTP.

Score/statutLivraison au modèle
Clean, 80–100 par défautTexte marqué entre délimiteurs UNTRUSTED-EXTERNAL-DATA.
Caution, 50–79UTF-8 Base64 marqué entre délimiteurs UNTRUSTED-EXTERNAL-DATA-BASE64.
Low, 0–49Contenu retenu et remplacé par un marqueur avec le score.

Base64 n’est ni du chiffrement ni une frontière de sécurité. Le modèle peut le décoder et doit toujours traiter le texte décodé comme une donnée, jamais comme une instruction.

Projections compactes et lots

Gmail et HTTP éliminent le boilerplate et les suffixes hors budget avant tout appel modèle. Chaque omission est représentée par des compteurs de caractères ou un marqueur applicatif. La compaction est une frontière de minimisation, pas une preuve que le texte omis était sûr. Les messages Gmail sont traités par lots stables de 12 éléments maximum et trois phases éligibles ; un lot en échec n’est pas rejoué message par message.

  • Gmail livre en cas de succès From, To, Subject et Received projetés avec un résumé factuel protégé. Snippet, Body, historique cité et suffixes omis n’atteignent jamais le contexte du workflow.
  • http.getText livre uniquement un résumé protégé du texte lisible compact. http.get livre un préfixe compact protégé adapté au média et n’est jamais résumé.
  • Une limite Gmail positive traite seulement les N premiers messages avec des compteurs et un avertissement ; 0 signifie illimité.
Un résumé généré peut omettre des détails. Relisez le message original dans Gmail ou l’URL source lorsque l’exhaustivité est importante.

Page Trust filter

Collez un exemple externe, choisissez éventuellement Return Base64, puis cliquez sur Screen. La page distingue le statut de confiance du statut de traitement, montre score, fournisseur, latence, longueurs, aperçu protégé et indicateurs verbatim. Ces indicateurs restent réservés à cette page ; les sorties Gmail/HTTP/Web Search n’exposent que leur nombre.

Réglages, confidentialité et limites

La section Settings → General → Guardrails règle les seuils, tailles, synthèse, délai, cache de 24 heures et limite Gmail. Désactiver Use LLM guardrails processing ne désactive pas la protection : les blocs de relecture Gmail/HTTP compacts utilisent le Base64 marqué lorsque le classement est indisponible.

Avec OpenAI-compatible, le contenu Gmail/HTTP/Web Search classé quitte la machine. Seules la projection compacte et le résumé généré sont envoyés ; le texte omis est supprimé auparavant. N’utilisez pas de véritable courrier privé pendant un test cloud sans autorisation explicite.

Les faux positifs et faux négatifs restent possibles, notamment face aux charges codées ou obfusquées. Dropbox, fichiers locaux, Calendar, pièces jointes Gmail, contenus sortants et réponses HTTP POST sont hors périmètre.

La page Tasks possède aussi son propre défilement vertical : les actions et la sortie restent donc accessibles lorsque le panneau est plus haut.

Une lecture Gmail signale la fin des projections puis une progression Guardrails sans contenu sous la forme batch N of M, avec des comptes agrégés. Avec une limite Gmail à zéro et sans maxMessages, chaque message remonté est projeté et inclus dans des lots bornés. Définir une limite reste un choix explicite : les messages au-delà sont signalés comme non traités.

Page Logs

  • Le flux est en lecture seule et suit automatiquement les nouvelles entrées.
  • Le filtre Level isole Information, Warning, Error, etc.
  • Source recherche un composant ou un contexte.
  • Task id limite l’affichage à une tâche précise.

Page Runs

Les exécutions planifiées se déroulent désormais sans aucune fenêtre visible. À la place, chaque exécution du runner — déclenchée par le Planificateur Windows ou par Run now — écrit un journal complet sur disque, ligne par ligne. La page Runs exploite ces journaux :

  • La liste de gauche montre chaque exécution avec l’id de tâche, l’heure de début locale et le statut : Success, Failed (code) ou In progress.
  • Sélectionnez une exécution en cours pour la suivre en direct. La page peut « prendre le train en marche » : le journal est relu depuis le début, aucune ligne n’est perdue même si la page est ouverte après le lancement.
  • Sélectionnez une exécution passée pour rejouer et inspecter tout son déroulé.
  • Line limit borne uniquement l’affichage (2 000 lignes par défaut) ; le fichier conserve tout.
  • Clear display vide seulement l’écran ; resélectionner l’exécution recharge le journal.
  • Save as… exporte l’exécution sélectionnée en texte brut ; Open folder ouvre le dossier des journaux.
  • Auto-scroll suit les nouvelles lignes et peut être suspendue, comme sur la page Tasks.
  • Chaque entrée est affichée de manière compacte : une ligne de journal ne crée pas artificiellement une ligne blanche supplémentaire.

Les journaux sont conservés sous <FileSystem:RootPath>\.od-my-local-agent\logs\runs\<taskId>\ (50 fichiers par tâche par défaut, réglable via Logging:MaxRunLogsPerTask). Ils contiennent la même sortie que la console du runner : traitez-les comme des données de diagnostic privées, au même titre que les rapports. Les canaux de contexte et de debug éphémères n’y sont jamais enregistrés.

Pour lancer manuellement le runner depuis PowerShell, la sortie s’affiche toujours dans la console appelante ; elle peut s’entrelacer avec l’invite — appuyez sur Entrée pour retrouver une invite propre.

Une tâche marquée Failure doit être examinée dans cet ordre : sortie du runner, rapport de la tâche, page Logs, puis incident éventuel avec son correlation id.

Archives, documents Office et PDF

Archives, Word documents, Spreadsheets et PDF documents sont indépendants et décochés pour une nouvelle tâche. Un groupe n’accorde jamais un chemin, et un chemin n’active jamais un groupe. Accordez ReadOnly à chaque entrée et ReadWrite à chaque sortie. Extraction, création et ajout d’archives exigent aussi la capacité de tâche ArchiveWrite ; elle n’accorde ni groupe ni chemin.

Données non fiables : noms d’archives, textes, feuilles, cellules et métadonnées PDF peuvent contenir des instructions trompeuses. Les limites obligatoires sont appliquées avant l’entrée du contenu dans un agent ou workflow.

Formats et limites

Formats de lecture/extraction : ZIP, 7z, RAR, TAR, TAR.GZ/TGZ, TAR.BZ2/TBZ2, TAR.LZ, TAR.XZ/TXZ, TAR.ZST/TZST, GZIP, BZIP2, LZIP, XZ et Zstandard, avec validation de l’extension et du contenu. Seul ZIP est inscriptible. DOCX, valeurs stockées XLS/XLSX/XLSB, métadonnées et texte PDF sont en lecture seule et analysés localement ; aucune application de bureau n’est ouverte.

Plafonds livrés : entrée 100 Mio ; 10 000 entrées d’archive ; 250 Mio par entrée extraite ; 1 Gio au total ; ratio 200 ; 1 000 entrées listées ; 64 000 caractères ; 1 000 lignes ; 256 colonnes ; 25 000 cellules ; 100 pages PDF. Settings permet uniquement des valeurs dans les bornes validées ; aucune valeur ne désactive une limite.

1. Extraire une entrée ZIP

Activez Archives, accordez ReadOnly à work/in.zip et ReadWrite à work/output/readme.txt, accordez ArchiveWrite, puis utilisez :

{ "id": "extract-one", "tool": "archive.extract", "arguments": {
  "archivePath": "work/in.zip", "entryPath": "docs/readme.txt",
  "destinationPath": "work/output/readme.txt", "overwrite": false
} }

2. Extraire une archive complète

Le parent de destination doit exister, mais work/output/package ne doit pas exister. Le résultat complet est préparé puis renommé seulement après validation.

{ "id": "extract-all", "tool": "archive.extractAll", "arguments": {
  "archivePath": "work/in.7z", "destinationDirectory": "work/output/package"
} }

3. Créer un ZIP, puis ajouter un fichier

La création utilise deflate/balanced par défaut ; l’écrasement vaut false. La seconde étape montre store, qui interdit compressionLevel. Les niveaux Deflate sont exactement fast, balanced et smallest.

[
  { "id": "create", "tool": "archive.createZip", "arguments": {
    "archivePath": "work/output/bundle.zip", "sourcePath": "work/input/first.txt"
  } },
  { "id": "add", "tool": "archive.addToZip", "arguments": {
    "archivePath": "work/output/bundle.zip", "sourcePath": "work/input/second.txt",
    "entryPath": "documents/second.txt", "overwriteEntry": false, "compressionMethod": "store"
  } }
]

Création et ajout construisent puis valident un ZIP voisin complet avant remplacement. L’ancien ZIP survit aux erreurs de construction, d’analyse, de limite ou d’annulation.

4. Lire un DOCX

{ "id": "read-docx", "tool": "document.readDocx", "arguments": {
  "documentPath": "work/docs/notes.docx", "maxCharacters": 12000
} }

Paragraphes du corps, tabulations, sauts, tableaux, texte affiché des hyperliens et insertions courantes sont inclus. En-têtes, pieds de page, commentaires, notes, zones de texte, images/texte alternatif, révisions supprimées, packages incorporés, XML personnalisé et relations externes sont omis. La source n’est jamais écrite.

5. Lister les feuilles et lire une plage bornée

[
  { "id": "sheets", "tool": "spreadsheet.listSheets", "arguments": {
    "workbookPath": "work/data/report.xlsx"
  } },
  { "id": "range", "tool": "spreadsheet.readRange", "arguments": {
    "workbookPath": "work/data/report.xlsx", "sheetName": "Summary",
    "startRow": 2, "startColumn": 1, "maxRows": 100, "maxColumns": 8
  } }
]

Les cellules portent un type stable. Formules, macros, liens, requêtes et connexions ne sont jamais exécutés ni actualisés ; seules les valeurs stockées/en cache sont renvoyées, donc une formule peut être périmée. Le classeur n’est jamais écrit.

6. Lire des pages PDF sélectionnées

[
  { "id": "pdf-info", "tool": "pdf.getInfo", "arguments": {
    "pdfPath": "work/docs/report.pdf"
  } },
  { "id": "pdf-pages", "tool": "pdf.readText", "arguments": {
    "pdfPath": "work/docs/report.pdf", "startPage": 3,
    "maxPages": 5, "maxCharacters": 16000
  } }
]

Il s’agit d’extraction textuelle tenant compte de la mise en page, pas d’OCR. Une page image renvoie un texte vide et hasExtractableText: false. Colonnes, ligatures, scans et polices inhabituelles peuvent rendre l’ordre incomplet. Aucun rendu, édition, signature, remplissage, extraction de pièce jointe, JavaScript ou accès à un lien.

Knowledge embarqué et RAG

Ouvrez Knowledge pour importer des documents TXT, Markdown, DOCX ou PDF textuels. Les fichiers sont copiés dans l’espace privé de l’application, extraits, découpés de façon déterministe puis vectorisés localement. L’OCR n’est pas fourni, les PDF constitués uniquement d’images ne sont pas pris en charge et les données Knowledge ne sont pas chiffrées au repos.

Configurez et testez le fournisseur et le modèle indépendants dans Settings → Knowledge embeddings. Ollama utilise par défaut embeddinggemma:300m. Un changement de modèle ou de contrat de découpage exige Reindex library ; l’ancien index complet reste actif si la reconstruction échoue ou est annulée.

L’accès est refusé par défaut. Activez le groupe ordinaire knowledge pour une tâche ou une conversation Direct Chat, puis sélectionnez explicitement les tags de la bibliothèque. Une portée vide n’accorde aucun document. Une étape de workflow ai.prompt peut déclarer l’alias exact knowledge.search et restreindre, mais jamais élargir, les tags de la tâche.

La recherche hybride combine une correspondance exacte des termes et une recherche sémantique, puis privilégie des extraits complémentaires. Elle peut ajouter le contexte immédiatement voisin d’une même section et d’une même page, dans des limites globales définies dans Settings → Knowledge embeddings. Ces réglages changent le comportement de recherche pour toute la bibliothèque ; ils ne modifient pas les droits d’accès. Une correspondance exacte ne prouve pas qu’un document est fiable ou complet. La recherche n’a lieu que lorsque l’agent appelle l’outil ; les extraits sont des données non fiables et ne sont jamais injectés automatiquement.

Autorisations sensibles par tâche

Les opérations sensibles sont refusées par défaut. Il n’existe plus de bouton Safety global. Une tâche doit accorder explicitement la capacité requise, en plus de sa liste blanche de groupes et de ses règles d’accès aux fichiers. PowerShell et Shell Execute sont des droits distincts. Les anciennes tâches sans champ capabilities ne reçoivent aucun droit sensible.

Le dialogue Edit workflow text modifie atomiquement les prompts IA longs et les scripts PowerShell en préservant l’identité, l’ordre, le type et les autres arguments des étapes.

Éditeur d’étape de workflow

Placez le curseur dans un JSON de workflow valide, puis choisissez Insert before, Insert after, Edit step ou Delete step. Le formulaire est généré à partir du Tool Map. Une étape existante ne peut pas être convertie vers un autre outil : supprimez-la puis insérez son remplacement.

Pour ai.prompt et filesystem.write, Repeat for each item ajoute un sélecteur de tableau antérieur. L’éditeur signale aussi un chemin d’écriture identique à chaque passage lorsqu’aucun placeholder {{foreach.*}} n’apparaît dans le chemin.

La suppression avertit lorsqu’une étape ultérieure utilise le placeholder de sortie concerné. Les groupes d’outils et capacités sensibles sont proposés décochés et ne changent que si vous les acceptez explicitement. Les changements restent dans le brouillon jusqu’à Save task.

Dans une étape ai.prompt, sélectionnez les outils exacts dans la liste du catalogue. Le modèle, Temperature, Top P et le raisonnement peuvent hériter indépendamment. La portée Knowledge n’apparaît que si knowledge.search est sélectionné : conservez la portée de la tâche ou réduisez-la à un ou plusieurs tags déjà autorisés. Les chemins locaux absolus peuvent proposer des répertoires décochés et signaler une racine, un chemin UNC ou une portée élargie. Annuler ou fermer abandonne toute la copie de travail après confirmation ; Apply valide la tâche provisoire complète et n’exécute aucun outil.
